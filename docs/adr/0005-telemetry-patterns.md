# ADR-0005. Шаблони каналу телеметрії: публікація — підписка і буферизація на периферії

## Статус

Прийнято, 2026-11-16. Спирається на вимірювання ЛР3:
- [telemetry.md](../telemetry.md) — канал і політика помилок;
- [deployment.md](../deployment.md) — розрив зв'язку, навантаження;
- [results/load.csv](../../results/load.csv), [results/bottleneck.csv](../../results/bottleneck.csv), [results/bridge.txt](../../results/bridge.txt).

Уточнює ADR-0002 у двох пунктах:
- періодичні відліки D-05 у мережі периферії публікуються з QoS 0 і порядковим номером (а не з QoS 1);
- надійність забезпечує шлюз на ланці периферія — сервер.

## Контекст

Телеметрія ультразвукових датчиків (D-05, D-06) іде від Sensor Controllers через Telemetry Broker на Edge Node до сервера. Чинні вимоги:

| Вимога | Що означає для каналу |
|---|---|
| NFR-03 | Розрив Edge Node — сервер до 30 хв: 0 утрачених подій; після відновлення події синхронізуються ≤ 120 с |
| NFR-06 | ε = 1 − Nотр / Nнад ≤ 0,1 % відліків за добу |
| FR-09 | Пристрій без heartbeat 30 с позначається недоступним |
| FR-01, FR-02, FR-05 | Стан місця споживають кілька складників (Occupancy Fusion, Information Board, Sensor Ingest); у ЛР4 додасться модель |
| A-04, C-05 | WAN доступний 99,5 % часу; нестабільне з'єднання — штатна ситуація |

Ресурси: на Edge Node телеметрії виділено 0,25 CPU для шлюзу й 0,5 CPU для брокера (NFR-02: ρ вузла ≤ 0,7); смуга для телеметрії в WAN — 1 Мбіт/с.

## Варіанти

**Взаємодія датчиків і споживачів:**

1. Точка — точка: Sensor Controller надсилає HTTP-запит кожному споживачеві.
2. Публікація — підписка через Telemetry Broker (MQTT).

**Перенесення даних через розрив ланки периферія — сервер:**

- А. Без буфера: шлюз пересилає з QoS 0, як отримав.
- Б. Міст Mosquitto (`connection`, `cleansession false`, `persistence true`) — без власного коду.
- В. Власний шлюз зі стійким буфером SQLite (store-and-forward), QoS 1, видалення після PUBACK.

| Критерій | А. Без буфера | Б. Міст Mosquitto | В. Шлюз із буфером SQLite |
|---|---|---|---|
| Утрати за розриву 60 с, λ = 300 повідомлень/с | Усе за час розриву (≈ 18 000) | ε = 0,486 (19 331 — увесь розрив); з `upgrade_outgoing_qos` — ε = 0,33–0,38: черга є, але вивантажується без обмеження швидкості й переповнює чергу підписника на сервері (виміряно) | 0 (виміряно) |
| Дублікати після відновлення | — | 0 | 100 — одна пачка (виміряно) |
| Швидкість вивантаження після розриву | — | Не обмежена: зворотного тиску немає | Обмежена смугою (≈ 1000 записів/с) — підписник встигає |
| Стійкість буфера до аварії процесу | — | Знімок черги раз на `autosave_interval` | Журнал WAL: кожна транзакція |
| Що відкидається при переповненні | — | Нові повідомлення | Найстаріші (керовано, лічильник `відкинуто`) |
| Обмеження смуги ланки | Немає | Немає | `UPLINK_KBPS` |
| Обсяг коду й супроводу | Мінімальний | Лише конфігурація | ≈ 100 рядків Python, тести розриву |

## Рішення

1. **Публікація — підписка** (варіант 2) для всієї сенсорної телеметрії:
   - теми `p1/{зона}/{пристрій}/{tele|state}`;
   - показ — QoS 0 з (`dev`, `boot`, `seq`, `ts`);
   - стан — збережене повідомлення з QoS 1 і заповітом `offline`;
   - Keep Alive датчика 20 с: 1,5 · 20 = 30 с відповідає FR-09.
2. **Буферизація на периферії** (варіант В):
   - `gateway.py` пише кожне повідомлення в `outbox` до надсилання;
   - надсилає найстаріші пачками по 100 із QoS 1 і видаляє лише після PUBACK;
   - `MAX_ROWS` = 50 000 для зони з трьох датчиків;
   - для всієї парковки місткість рахується за (4) (deployment.md, «Масштабованість»);
   - при переповненні відкидаються найстаріші покази.
3. **Ідемпотентний приймач.** Підписник має постійну сесію (`clean_session=False`) і відкидає дублікати за первинним ключем (`dev`, `boot`, `seq`).
4. **Міст Mosquitto** (варіант Б) відхилено за вимірюванням: навіть із `upgrade_outgoing_qos` він утратив 33–38 % показів розриву. Причина — вивантаження без зворотного тиску переповнило чергу підписника на серверному брокері (deployment.md, «Розрив зв’язку»).
5. **Кероване зниження якості** не реалізується в коді цієї версії. Драбину Р0/Р1 спроєктовано (deployment.md, «Шаблони») і вмикатимемо, якщо навантаження наблизиться до Θ.

## Наслідки

### Позитивні

- ε = 0 за розриву 60 с при λ = 300 повідомлень/с: 40 270 надісланих = 40 270 отриманих; 100 дублікатів відкинуто ключем;
- вивантаження Q0 ≈ 18 450 записів тривало 30,7 с проти 26 с за формулою (5);
- новий споживач — одна підписка: два підписники додано без змін датчиків і `collector.py`; стан пристрою новий підписник отримує одразу;
- зникнення пристрою виявляється за 31 с (FR-09);
- канал виявляє пропуски, дублікати й позачергові покази точно: 47/47, 26/26, 38/38;
- бюджет NFR-06 за QoS 0 у мережі периферії — ≈ 86 с недоступності Telemetry Broker на добу.

### Негативні

- PUBACK підтверджує лише серверний брокер: підписник, що не працював 13 с при 300 повідомленнях/с, утратив 2335 показів — черга брокера (`max_queued_messages` = 1000) переповнилася вже після PUBACK. Для цільової системи потрібні `max_queued_messages` ≥ λ · Tперезапуску й `persistence true` на серверному брокері або підтвердження від приймача (HTTP 200 після запису в Metadata DB, як у ADR-0002);
- кожен показ записується на диск Edge Node: за 600 повідомлень/с — ≈ 75 КБ/с, ≈ 6,5 ГБ на добу запису на SSD (без урахування WAL);
- шлюз помічає розрив лише через 16 с (Keep Alive 10 с); весь цей час покази затримуються, хоч і не губляться;
- після розриву приходять дублікати (до розміру пачки, 100), тож усі споживачі мають бути ідемпотентними;
- покази QoS 0 між датчиком і Telemetry Broker губляться під час перезапуску брокера (46 за 3 с) — це прийнято в межах бюджету NFR-06;
- шлюз — ще один процес на Edge Node, який треба супроводжувати й спостерігати (`буфер`, `відкинуто`, `зв’язок`).

### Перевірка

- Повторювати експеримент розриву на 60 с (deployment.md, «Розрив зв’язку») після кожної зміни шлюзу: ε = 0, час вивантаження в межах ±20 % від (5).
- Для цільової парковки — розрив 30 хв (NFR-03) на стенді з повним навантаженням.
