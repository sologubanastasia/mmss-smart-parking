# ADR-0006. Мова й технологічний стек периферійного шлюзу

## Статус

Прийнято, 2026-11-16. Спирається на вимірювання ЛР3:
- [results/load.csv](../../results/load.csv), [results/load_gateway.log](../../results/load_gateway.log) — навантажувальне випробування;
- [results/bottleneck.csv](../../results/bottleneck.csv) — пошук вузького місця;
- [deployment.md](../deployment.md), розділи «Навантаження» і «Мова і стек».

Переглядається, якщо зміниться схема публікації або ресурси Edge Node (див. «Перевірка»).

## Контекст

Шлюз (Sync Agent із Local Event Buffer, ADR-0005) — єдиний складник, через який уся сенсорна телеметрія Edge Node іде на сервер. Навантажувальне випробування показало, що саме він обмежує пропускну здатність каналу Θ.

Вимоги до шлюзу:

| Вимога | Джерело | Число |
|---|---|---|
| Безперервна робота, буфер переживає аварію процесу | NFR-03, ADR-0005 | Журнал WAL, видалення лише після PUBACK |
| Обмежений процесор | NFR-02 (ρ Edge Node ≤ 0,7), Video Analytics забирає більшість | 0,25 CPU |
| Пам'ять | Edge Node 64 ГБ, ліміт контейнера | ≤ 128 МБ |
| Пропускна здатність із запасом u ≤ 0,5 | Розділ «Масштабованість» deployment.md | Θ ≥ 300 повідомлень/с за пакетної публікації (λ = 150); Θ ≥ 1200 — за окремих повідомлень від кожного датчика (λ = 600) |
| Конкурентність | Два з'єднання MQTT + диск | Приймання не повинно зупиняти надсилання |
| Бібліотеки | MQTT 3.1.1/5 з QoS 1 і відстеженням PUBACK; вбудована БД | — |
| Супровід | Ті самі люди супроводжують конвеєр ЛР2 (Python) | Один образ для емулятора, шлюзу й підписника |

Виміряно для Python 3.14 + paho-mqtt 2.1.0 + sqlite3 (deployment.md):

| Конфігурація | Результат |
|---|---|
| 0,25 CPU, смуга 1000 кбіт/с | Θ ≈ 550 повідомлень/с. Під перевантаженням падає до ≈ 270 (λ = 1500): приймання забирає процесор у надсилання. Без вхідного потоку шлюз вивантажує ≈ 1000 повідомлень/с, тобто впирається в смугу |
| 0,25 CPU, смуга не обмежена | λ = 900: буфер переповнився, ε = 0,084 (з обмеженням смуги — 0,082) — смуга не є вузьким місцем |
| 1 CPU, смуга 1000 кбіт/с | λ = 900: буфер ≤ 24 записи, ε = 0, Lд сер. 18,7 мс — вузьке місце саме процесор |
| Пам'ять | 15,5 МіБ у спокої, 22,5 МіБ пік при повному буфері |

| Варіант | Модель конкурентності | Пам'ять | Θ на 0,25 CPU | Стійкість буфера | Супровід |
|---|---|---|---|---|---|

## Рішення

1. **Python 3.14 + paho-mqtt 2.1.0 + sqlite3** для шлюзу цієї версії. Обґрунтування:
   - за пакетної публікації ЛР1 (λ = 150 повідомлень/с для всієї парковки) виміряна Θ ≈ 550 дає u ≈ 0,27 — запас 3,7 раза;
   - для трьох датчиків прототипу (3 повідомлення/с) запас ≈ 180 разів;
   - пам'ять ≤ 22,5 МіБ із 128 МБ;
   - спільний образ з емулятором і підписником; Python уже супроводжується в конвеєрі ЛР2.
2. **Першим кроком масштабування є вертикальне.** Перехід на іншу мову — другий крок. 1 CPU замість 0,25 прибрав вузьке місце на λ = 900, а Edge Node має 16 CPU. Тому за потреби шлюзові спершу дають 0,5–1 CPU.
3. **Умови переходу на Go** (варіант 2) — будь-яка з них:
   - окремі повідомлення від кожного датчика (λ = 600 > Θ) без можливості виділити більше CPU;
   - один шлюз на кілька парковок (fog-вузол);
   - Edge Node на ARM з менш ніж одним ядром для телеметрії;
   - тривале u > 0,5 за метрикою `буфер`.
4. **Міст Mosquitto** (варіант 4) не використовується. Виміряно: за розриву 60 с він утратив 36–49 % показів, бо вивантажує чергу без обмеження швидкості. Крім того, при переповненні він відкидає нові повідомлення, а черга переживає аварію лише як знімок.

## Наслідки

### Позитивні

- один мовний стек для емулятора, шлюзу, підписника й аналітики (stats.py, plot.py), один образ Docker на 181 МБ;
- код шлюзу короткий (≈ 100 рядків) і читається як опис шаблону store-and-forward, що спрощує захист і супровід;
- запас Θ для цільового навантаження з пакетною публікацією — 3,7 раза, а з 1 CPU — щонайменше 6 разів (λ = 900 без зростання буфера);
- SQLite входить до стандартної бібліотеки Python: немає окремого сервера БД на периферії.

### Негативні

- Θ на 0,25 CPU (≈ 550) нижча за потрібні 600 повідомлень/с, якщо кожен датчик публікує окремо. Ця схема з Python на 0,25 CPU не працює для всієї парковки;
- під перевантаженням Θ падає (550 → 270), бо приймання й запис нових повідомлень забирають процесор у надсилання. Без керованого зниження якості (ADR-0005) перевантаження самопідсилюється;
- головний цикл опитує буфер без пауз, поки в ньому є записи, тож `docker stats` показує ≈ 25 % навіть за λ = 300. Процесор як метрика навантаження шлюзу непридатний; спостерігати треба `буфер`;
- GIL не дає використати кілька ядер, тож горизонтальне масштабування — лише кількома процесами (шлюз на зону);
- образ `python:3.14-slim` важчий за статичний бінарний файл Go (181 МБ проти ≈ 10–20 МБ), що важливо для оновлень на багатьох парковках.

### Перевірка

- Після будь-якої зміни шлюзу повторити `bash smart/loadtest.sh`: Θ на 0,25 CPU не нижча за 500 повідомлень/с, ε = 0 до λ = 600.
- Якщо планується публікація кожного датчика окремо — повторити `bash smart/bottleneck.sh` з `cpus` 0,5 і 1,0 і порівняти з прототипом шлюзу на Go на тих самих ступенях.
