# ЛР3, заняття 1. Канал сенсорних даних

Канал повторює сенсорну частину системи розумної парковки з ЛР1. Ультразвукові датчики Ultrasonic Sensors над паркомісцями зони A через Sensor Controllers публікують періодичні відліки відстані (потік D-05 реєстру даних, публікація 1 Гц) у Telemetry Broker. Підписник Sensor Ingest перевіряє їх і зберігає.

| Складник ЛР3 | Файл | Елемент ЛР1 (табл. 11.1 requirements.md) |
|---|---|---|
| Емулятор трьох датчиків місць A-017, A-018, A-019 | [smart/sensors.py](../smart/sensors.py) | Ultrasonic Sensors, Sensor Controllers |
| Брокер Eclipse Mosquitto 2.1.2 | [smart/broker/mosquitto.conf](../smart/broker/mosquitto.conf) | Telemetry Broker |
| Підписник зі сховищем SQLite | [smart/collector.py](../smart/collector.py) | Sensor Ingest |
| Підсумок каналу | [smart/stats.py](../smart/stats.py) | Local Metrics (показники каналу) |

Модель відліку: датчик висить над місцем на висоті 2500 мм. Порожнє місце дає ≈ 2500 мм (відстань до покриття), зайняте — ≈ 1000 мм (до даху авто), шум σ = 6 мм. Місця змінюють стан з різними періодами (стоянка 13–37 хв), тож потік схожий на реальний. Діапазон датчика взято з даташита ультразвукового далекоміра класу MaxBotix HRXL-MaxSonar-WR: 300–5000 мм, роздільність 1 мм.

Свідомі спрощення порівняно з ЛР1:
- JSON замість Protobuf;
- окреме повідомлення від кожного датчика замість пакета з 10 відліків;
- брокер без TLS, але доступний лише з 127.0.0.1.

Схема зберігає всі поля Protobuf-схеми з ADR-0002 (табл. у розділі «Схема повідомлення»), тож перехід на Protobuf змінює лише кодування.

## Теми

Тема має чотири рівні: `p1/{зона}/{пристрій}/{вид}`.

| Рівень | Значення | Приклад |
|---|---|---|
| 1. Парковка | Ідентифікатор об'єкта; дає змогу обслуговувати кілька парковок одним сервером | `p1` |
| 2. Зона | Одна з 5 зон по 100 місць (`za` … `ze`) | `za` |
| 3. Пристрій | Тип і номер: `us-017` — ультразвуковий датчик місця A-017 | `us-017` |
| 4. Вид повідомлення | `tele` — показ, `state` — доступність пристрою | `tele` |

| Тема | Публікує | Вміст | QoS | Збережене (retain) | Підписники |
|---|---|---|---|---|---|
| `p1/za/us-017/tele` | Датчик | Показ за схемою (нижче) | 0 | Ні | `collector.py` (`p1/+/+/tele`); у занятті 2 — шлюз |
| `p1/za/us-017/state` | Датчик (`online`), брокер (заповіт `offline`) | `online` / `offline` | 1 | Так | Оператор, Device Registry (`p1/+/+/state`) |

Шаблони підписки:
- `p1/+/+/tele` — уся телеметрія парковки;
- `p1/za/#` — усе по зоні A;
- `p1/+/+/state` — доступність усіх пристроїв.

Новий споживач додається підпискою, без змін у сенсорах.

**Чому телеметрія йде з QoS 0.** Відлік D-05 повторюється щосекунди, і наступний замінює загублений. NFR-06 допускає ε ≤ 0,1 % на добу. Утрату виявляє `seq` (формула (1)), тож підтвердження кожного показу не потрібне. QoS 1 додав би на кожен показ пакет PUBACK і стан повідомлення на брокері. У мережі периферії TCP не губить пакетів, тож за QoS 0 покази губляться лише під час розриву з брокером. Перевірка нижче показала, що 3 с розриву коштують 3 с даних. Для 500 датчиків бюджет NFR-06 — 0,001 · 500 · 86 400 = 43 200 відліків на добу, тобто ≈ 86 с повної недоступності Telemetry Broker на добу.

Надійна доставка потрібна там, де втрати не допускаються:
- ланка периферія — сервер (шлюз із QoS 1, заняття 2);
- події зміни стану D-06 (QoS 1; у роботі не емулюються).

Тому ADR-0002 уточнено в ADR-0005: QoS 0 для періодичних відліків у мережі периферії.

**Стан пристрою.** Повідомлення `online` збережене (retain), тож новий підписник одразу отримує поточний стан. Заповіт `offline` брокер публікує сам, якщо датчик зник без від'єднання. Keep Alive датчика — 20 с: брокер виявляє зникнення через 1,5 · 20 = 30 с, як вимагає FR-09 («після 30 с без heartbeat пристрій позначається недоступним»).

## Схема повідомлення

```json
{"dev":"za-us-017","boot":2,"seq":586,"ts":"2026-11-16T13:38:10.687Z","qty":"dist","val":2500,"unit":"mm"}
```

| Поле | Тип JSON | Одиниця або формат | Призначення — на яке запитання споживача відповідає | Діапазон, перевірка | Поле Protobuf (ADR-0002) |
|---|---|---|---|---|---|
| `dev` | string | `{зона}-{пристрій}` | Який пристрій виміряв? | Збігається з рівнями 2–3 теми | `device_id` |
| `boot` | integer | Номер запуску | Чи перезапускався пристрій і чи почав `seq` спочатку? | ≥ 1; лічильник у постійній пам'яті (`data/boot.txt`, у занятті 2 — том) | `boot_id` |
| `seq` | integer | Порядковий номер у межах (`dev`, `boot`) | Чи все отримано й у якому порядку? | ≥ 0; формула (1) | `seq` |
| `ts` | string | ISO 8601 UTC, мс: `YYYY-MM-DDTHH:MM:SS.sssZ` | Коли виміряно? | Не пізніше ніж годинник сервера + 5 с; похибка годинника ≤ 10 мс (NFR-04) | `ts_capture` |
| `qty` | string | Код величини | Що виміряно? | Відома величина: `dist` | (тип поля) |
| `val` | number | — | Яке значення? | Для `dist` 300–5000 (даташит) | `distance_mm` |
| `unit` | string | Код одиниці UCUM | У яких одиницях? | Для `dist` лише `mm` | (у назві поля) |

Обсяг одного повідомлення: s = 17 Б (тема) + 106 Б (тіло) ≈ 123 Б. Порядковий номер і номер запуску до 5 цифр дають ≈ 126 Б. Те саме в Protobuf займає ≈ 32 Б (requirements, 6.3), тобто JSON утричі-вчетверо більший.

Значення `boot` і `seq` дають підписникові формули (1) і (2):

- nk = sk − sk−1 − 1 — пропущені перед k-м показом (nk > 0 — пропуск, nk < 0 — позачерговий або дублікат);
- ε = 1 − Nотр / Nнад, де Nнад = max(seq) − min(seq) + 1 у межах запуску.

Затримку доставки підписник обчислює для кожного показу: Lд = tотр − tвим, де tвим — `ts`. Усі складники працюють на одному комп'ютері з одним годинником. На парковці годинники синхронізує Time Synchronizer (NTP, похибка ≤ 10 мс).

## Політика оброблення помилок

Відхилене повідомлення з причиною потрапляє до таблиці `rejected`: специфікація MQTT черги недоставлених повідомлень не визначає, тож цю роль виконує застосунок. Первинний ключ `readings` — трійка (`dev`, `boot`, `seq`), тож дублікат відкидає сама база.

| № | Ситуація | Як виявляється | Дія | Де фіксується | Де реалізовано | Перевірено |
|---:|---|---|---|---|---|---|
| 1 | Не JSON (зіпсоване, обрізане) | `json.loads` | Відхилити, роботу не зупиняти | `rejected`, «не JSON» | `collector.py`, `validate()` | 39 з 39 внесених (`BAD`) |
| 2 | JSON, але не об'єкт | `isinstance(m, dict)` | Відхилити | `rejected`, «не об’єкт JSON» | `validate()` | `[2500]` |
| 3 | Немає поля | Перевірка за `FIELDS` | Відхилити | `rejected`, «немає поля …» | `validate()` | Без `unit` |
| 4 | Хибний тип поля, зокрема `true` замість числа | `isinstance`, окремо `bool` | Відхилити | `rejected`, «тип поля …» | `validate()` | `"seq":"1"`, `"boot":true` |
| 5 | `dev` не відповідає темі | `dev` = `{зона}-{пристрій}` з теми | Відхилити | `rejected` | `validate()` | `za-us-018` у темі `us-017` |
| 6 | Невідома величина | `qty` поза `QTY` | Відхилити | `rejected` | `validate()` | `"qty":"temp"` |
| 7 | Одиниця не відповідає величині | `unit` ≠ `QTY[qty]` | Відхилити | `rejected`, «одиниця» | `validate()` | `"unit":"cm"` |
| 8 | Значення поза діапазоном датчика | Межі з даташита: 300–5000 мм | Відхилити як недостовірне | `rejected`, «поза діапазоном» | `validate()`, `QTY` | `"val":6200` |
| 9 | `boot` < 1 або `seq` < 0 | Перевірка меж | Відхилити | `rejected`, «boot або seq» | `validate()` | `"boot":0` |
| 10 | Хибний формат мітки часу | `strptime` | Відхилити | `rejected`, «формат ts» | `validate()` | `"2026-11-16 08:00:00"` |
| 11 | Мітка часу з майбутнього | Більше ніж на 5 с від годинника сервера | Відхилити; перевірити синхронізацію (Time Synchronizer) | `rejected` | `validate()`, `FUTURE_MS` | `ts` + 60 с |
| 12 | Дублікат | Трійка (`dev`, `boot`, `seq`) уже є | Не зберігати повторно | `anomalies`, `dup` | `INSERT OR IGNORE`, первинний ключ | 26 з 26 (`DUP`) |
| 13 | Пропуск | nk > 0 за (1) | Зберегти показ, урахувати втрату | `anomalies`, `gap`, n | `on_message` | Сума n = 85 = 47 пропущених + 38 відкладених |
| 14 | Позачерговий показ | nk < 0, номера ще немає | Зберегти; пропуск зменшується | `anomalies`, `late` | `on_message` | 38 з 38 (`LATE`) |
| 15 | Перезапуск датчика | Новий `boot` | Почати лік номерів заново, не вважати пропуском | `readings` (новий ключ) | `next_boot()`, ключ `last` = (`dev`, `boot`) | Запуски 2 → 3 → 4 без хибних `gap` |
| 16 | Датчик завершився аварійно | ОС закриває TCP-з'єднання без DISCONNECT | Брокер публікує заповіт `offline` | Збережене `.../state` | `will_set()` у `sensors.py` | `offline` через < 1 с після `taskkill /F` |
| 17 | Датчик завис або втратив живлення | Немає пакетів 1,5 · Keep Alive = 30 с | Брокер позначає пристрій недоступним (FR-09) | Збережене `.../state` | `KEEPALIVE = 20` | `docker pause`: `offline` через 31 с |
| 18 | Розрив зв'язку з брокером | `on_connect` після перепідключення | Підписатися знову; покази QoS 0 за час розриву втрачено | `anomalies`, `gap` | `on_connect`, `loop_forever`, `loop_start` | Перезапуск брокера: 46 утрачених за ≈ 3 с, обидві сторони перепідключилися самі |

| 21 | Буфер шлюзу переповнено | Записів більше за `MAX_ROWS` | Відкинути найстаріші покази | Лічильник `відкинуто`; у підписника — `gap` | `gateway.py` | Заняття 2: `відкинуто` = сумі втрат підписника |
| 22 | Показ поза фізично можливим для місця (більше за висоту монтажу) — бруд, зміщення датчика | Порівняння з профілем пристрою | Позначити датчик несправним, місце — `UNCERTAIN` | — | **Не реалізовано:** потрібен профіль із висотою монтажу в Device Registry; поки діє лише межа даташита (рядок 8) | — |
| 23 | «Застиглий» показ (датчик повторює те саме значення) | Однакові значення довше за поріг | Тривога технічній службі | — | **Не реалізовано:** σ шуму 6 мм дає змогу виявити, але поріг треба обрати за реальними даними. Конфлікт з відеоканалом уже ловить Occupancy Fusion (FR-02) | — |

## Перевірка каналу

Брокер — `docker compose up -d` із [docker-compose.yml](../smart/docker-compose.yml) заняття 1. Підписник працював у другому терміналі.

**1. Емулятор** (`python smart/sensors.py`, зупинка через 4 с; у терміналі 2 `mosquitto_sub -t 'p1/#' -v -C 8`):

```text
boot=1, HZ=1.0, сенсорів: 3
p1/za/us-017/state online
p1/za/us-018/state online
p1/za/us-017/tele {"dev":"za-us-017","boot":1,"seq":0,"ts":"2026-11-16T13:38:10.687Z","qty":"dist","val":2500,"unit":"mm"}
p1/za/us-019/state online
p1/za/us-018/tele {"dev":"za-us-018","boot":1,"seq":0,"ts":"2026-11-16T13:38:11.020Z","qty":"dist","val":2497,"unit":"mm"}
p1/za/us-019/tele {"dev":"za-us-019","boot":1,"seq":0,"ts":"2026-11-16T13:38:11.354Z","qty":"dist","val":2503,"unit":"mm"}
p1/za/us-017/tele {"dev":"za-us-017","boot":1,"seq":1,"ts":"2026-11-16T13:38:11.687Z","qty":"dist","val":2510,"unit":"mm"}
p1/za/us-018/tele {"dev":"za-us-018","boot":1,"seq":1,"ts":"2026-11-16T13:38:12.020Z","qty":"dist","val":2499,"unit":"mm"}
```

**2. Внесені збої** (30 с, 20 повідомлень/с від кожного датчика):

```text
$ DROP=0.03 DUP=0.02 LATE=0.03 BAD=0.02 HZ=20 DURATION=30 python smart/sensors.py
boot=2, HZ=20.0, сенсорів: 3
Підсумок: {'published': 1753, 'drop': 47, 'dup': 26, 'late': 38, 'bad': 39}

$ python smart/stats.py
boot rate sent received   loss late dup lat_mean_ms lat_p95_ms lat_max_ms
   2 60.0 1800     1753 0.0261   38  26         3.0          3        103
Відхилено: не JSON — 39
```

| Показник | Внесено емулятором | Виявлено підписником | Збіг |
|---|---:|---:|---|
| Пропущені покази | `drop` = 47 | `sent` − `received` = 1800 − 1753 = 47 | Так |
| Позачергові | `late` = 38 | `late` = 38 | Так |
| Дублікати | `dup` = 26 | `dup` = 26 | Так |
| Зіпсовані | `bad` = 39 | «не JSON» = 39 | Так |
| Частка втрат | 47 / 1800 | ε = 1 − 1753 / 1800 = 0,0261 | Так |

Таблиця `anomalies` містить 80 записів `gap` із сумою n = 85. Це 47 справжніх пропусків плюс 38 відкладених показів: їх спершу пораховано пропущеними, а після надходження записано як `late` із nk < 0. Затримка доставки в мережі периферії: середня 3,0 мс, p95 3 мс, максимум 103 мс. Максимум припадає на позачергові покази, які емулятор свідомо надіслав пізніше.

**3. Політика помилок.** Кожен рядок 1–11 перевірено окремим повідомленням `mosquitto_pub` у тему `p1/za/us-017/tele`. Підсумок `stats.py`:

```text
Відхилено: boot або seq — 1, dev не відповідає темі — 1, мітка часу з майбутнього — 1, не JSON — 39,
не об’єкт JSON — 1, невідома величина — 1, немає поля unit — 1, одиниця — 1, поза діапазоном — 1,
тип поля boot — 1, тип поля seq — 1, формат ts — 1
```

**4. Зникнення датчика й розрив зв'язку** (рядки 16–18):

```text
# аварійне завершення емулятора (taskkill /F) о 13:39:56 — з'єднання закрито ОС
2026-11-16T13:39:56+0000 p1/za/us-019/state offline
# емулятор у контейнері призупинено (docker pause) о 13:42:54 — з'єднання «висить»
2026-11-16T13:43:25+0000 p1/za/us-018/state offline           # через 31 с ≈ 1,5 · 20 с
# перезапуск брокера о 13:44:05 під час запуску boot=4 (5 повідомлень/с від датчика)
boot rate sent received   loss late dup
   4 15.0  600      554 0.0767    0   0                        # 46 утрачено: 15 + 15 + 16
```

Під час перезапуску брокера емулятор звітував про 600 опублікованих показів, бо paho-mqtt мовчки відкидає QoS 0 без з'єднання. Утрату побачив лише підписник за `seq`. Саме тому схема має порядковий номер.

**Висновок.** Канал виявляє всі чотири види збоїв точно, без хибних спрацювань. Перезапуск датчика не дає хибних пропусків, бо ключ — пара (`dev`, `boot`). Зникнення пристрою брокер помічає за ≤ 31 с (FR-09). Слабке місце — покази QoS 0 під час розриву з брокером. На периферії їх покриває бюджет NFR-06, а ланку до сервера захищає шлюз заняття 2.

Під час перевірки виявилося ще одне правило: лічильник `boot` має жити в постійній пам'яті пристрою. Тестовий контейнер для рядка 17 мав власний лічильник і знову почав з `boot=1`, хоча цей номер уже використав запуск на хості (перевірка 1). Якби підписник тоді працював, покази обох запусків мали б той самий ключ (`za-us-017`, 1, `seq`), і нові відкидалися б як дублікати. Тому в занятті 2 лічильник лежить на томі `sensors-data`, який переживає перезапуск і перестворення контейнера.
