# Сценарії атрибутів якості

Сценарії сформульовано з нефункційних вимог ([requirements.md](requirements.md), розділ 8): показник вимоги стає мірою відповіді, умови вимірювання — середовищем. Перевірка виконується спрощеним ATAM (кроки 3–6): кожен крок сценарію проходиться по компонентному поданню й поданню розгортання з називанням складника, який його забезпечує.

## 1. Дерево корисності

Позначки: (важливість для замовника, складність реалізації); В — висока, С — середня, Н — низька.

| Атрибут | Уточнення | Листок дерева | Позначки | Сценарій |
|---|---|---|---|---|
| Швидкодія | Актуальність стану | Оновлення стану p95 ≤ 2 с за масової зміни стану й 200 клієнтів | (В, В) | QS-01 |
| Швидкодія | Реакція актуатора | Команда шлагбаума ≤ 1 с від появи авто | (В, С) | — |
| Доступність | Автономність | Робота без сервера 30 хв, 0 втрачених подій | (В, В) | QS-02 |
| Мультимодальність | Синхронність | Розходження міток каналів ≤ 250 мс для 99 % подій | (С, С) | — |
| Безпека | Доступ до медіа | 0 байт медіа без перевірки ролі, 100 % запитів в аудиті | (В, Н) | — |
| Масштабованість | Зростання кількості зон | 1 → 5 зон на одному edge-вузлі: p95 +≤ 20 %, ρ ≤ 0,7 | (С, С) | — |
| Супровідність | Заміна обладнання | Камера іншого виробника підімкнена за ≤ 4 год без змін коду | (С, Н) | — |

Обидва листки з парою (В, В) розібрано нижче як QS-01 і QS-02.

## QS-01. Масова зміна стану місць у пікову годину

**Атрибут:** швидкодія.

| Елемент | Опис |
|---|---|
| Джерело стимулу | Автомобілі, що масово виїжджають після події, і водії зі смартфонами |
| Стимул | Протягом 10 с змінюється стан 100 місць у 5 зонах, одночасно 200 клієнтів запитують карту |
| Середовище | Штатний режим: 50 камер, 500 датчиків, усі вузли доступні, ρ GPU до стимулу ≤ 0,4 |
| Артефакт | Video Analytics, Sensor Ingest, Time Synchronizer, Occupancy Fusion, Sync Agent, Parking API, Information Board |
| Реакція | Стан кожного місця оновлюється в Driver App і на табло; якщо ρ GPU перевищує 0,7, Video Analytics знижує частоту аналізу з 5 до 2,5 кадр/с для зон без змін; команди шлагбаума обслуговуються без затримки |
| Вимірювана характеристика | p95 затримки ≤ 2 с у Driver App і ≤ 1 с на табло; 0 % невдалих запитів клієнтів; p95 затримки команд зростає ≤ 10 % відносно штатного режиму |

**Забезпечується:** аналізом допоміжних потоків на edge-вузлі (ADR-0001), окремим Control Broker (ADR-0002), двома екземплярами Parking API за Load Balancer.

### Проходження сценарію по архітектурі

| Крок | Складник | Частка бюджету |
|---|---|---:|
| Захоплення кадру допоміжного потоку та відліку датчика з міткою часу | IP Cameras, Sensor Controllers | 250 мс |
| Класифікація ділянок кадру й підтвердження наступним кадром | Video Analytics | 300 мс |
| Вирівнювання міток і об'єднання у вікні W = 300 мс | Time Synchronizer, Occupancy Fusion | 300 мс |
| Запис у Local Event Buffer і передавання на сервер | Sync Agent | 200 мс |
| Збереження й розсилання через WebSocket | Parking API, Driver App | 300 мс |
| Паралельна гілка: лічильники зон на табло | Telemetry Broker, Information Board | 150 мс |
| **Разом до Driver App / до табло** | | **1350 / 1000 мс** |

Запас до цільових 2 с — 650 мс. Навантаження стимулу (10 подій/с) у 10 разів менше за піковий розрахунок D-06 (100 подій/с), тож Occupancy Fusion і Sync Agent не є вузьким місцем. Вузьким місцем може стати лише GPU.

### Тактики та їхня ціна

| Тактика | Що змінює | Що погіршує |
|---|---|---|
| Зниження попиту: аналіз 640×360, 5 кадр/с замість 1080p, 15 кадр/с (у 27 разів менше пікселів) | Час декодування й класифікації | Точність для дальніх місць — компенсується датчиком |
| Кероване зниження якості: 5 → 2,5 кадр/с для зон без змін за ρ > 0,7 | Попит на GPU удвічі | `Lсенс` +200 мс — укладається в запас 650 мс |
| Паралельне оброблення: окремий обробник Video Analytics на кожну зону | Пропускна здатність | Складність розгортання й моніторингу |
| Реплікація: Parking API ×2 за Load Balancer | Час відгуку для 200 клієнтів | Вартість; API має бути безстановим |

### Процедура перевірки

1. Запустити генератор 50 допоміжних і основних відеопотоків, 500 імітаторів датчиків і стендовий тригер міток `stimulus_time`.
2. Виміряти p95 затримки команд шлагбаума в штатному режимі (базова лінія).
3. За 10 с перевести 100 місць у новий стан, одночасно запустити 200 клієнтів k6, що запитують карту.
4. Зібрати мітки `stimulus_time`, `fusion_time`, `api_time`, `display_time`, `board_time` і ρ GPU (DCGM).
5. Обчислити p95 і порівняти з мірою відповіді.

### Критерій проходження

Усі чотири числові характеристики виконуються. Якщо p95 перевищує 2 с і ρ GPU > 0,7 — застосувати план NFR-02: поділити зони між двома edge-вузлами. Якщо затримка накопичується на сервері — додати екземпляр Parking API.

**Висновок:** архітектура підтримує сценарій із запасом 650 мс за умови, що вимірювання класифікатора в ЛР2 підтвердить A-05.

## QS-02. Розрив зв'язку edge-вузла з центральним сервером

**Атрибут:** доступність.

| Елемент | Опис |
|---|---|
| Джерело стимулу | Мережеве обладнання або провайдер зв'язку |
| Стимул | Канал між edge-вузлом і сервером зникає на 30 хв |
| Середовище | Штатна робота парковки: ≈ 85 в'їздів і виїздів за 30 хв (4000 подій на добу); кеш політик оновлено не раніше ніж за 60 с до розриву |
| Артефакт | LPR Service, Edge Access Control, Control Broker, Gate Controller, Occupancy Fusion, Local Event Buffer, Sync Agent, Web Console |
| Реакція | Визначення стану, табло, автоматичний в'їзд і виїзд для номерів із кешу та ручне керування працюють локально. Web Console показує режим «без сервера». Події накопичуються з унікальними `event_id`. Після відновлення Sync Agent першочергово передає події, а фрагменти — у фоні з лімітом 60 Мбіт/с |
| Вимірювана характеристика | 0 втрачених подій і підтверджених команд; команда шлагбаума ≤ 1 с у 50 тестах без зв'язку; події синхронізовано ≤ 120 с, фрагменти — ≤ 15 хв; 0 дублікатів у Metadata DB |

**Забезпечується:** Edge Access Control із кешем політик (ADR-0001), окремим Control Broker з TTL і підтвердженням команд (ADR-0002), Local Event Buffer з outbox та ідемпотентними `event_id`, подійним зберіганням фрагментів (ADR-0003).

### Проходження сценарію по архітектурі

| Крок | Складник |
|---|---|
| Sync Agent не отримує відповіді 10 с → режим «без сервера», повідомлення в Web Console | Sync Agent, Edge Access Control |
| Номер авто на в'їзді розпізнано | LPR Cameras, LPR Service |
| Рішення про доступ за кешем політик | Edge Access Control |
| Команда відкриття з TTL 5 с і підтвердженням | Control Broker, Gate Controller |
| Подія в'їзду записана з `event_id` | Local Event Buffer |
| Стан місць і лічильники табло оновлюються | Occupancy Fusion, Telemetry Broker, Information Board |
| Оператор керує вручну через локальну сторінку | Web Console, Edge Access Control |
| Після відновлення: дренаж буфера, події першими | Sync Agent, Parking API |
| Дедуплікація за `event_id`, закриття сесій, передавання на оплату | Parking API, Metadata DB, Session Service, Payment Adapter |

Кожен крок має складник-виконавця, і жоден не потребує сервера до моменту відновлення.

### Розрахунок синхронізації після відновлення

| Що накопичилося за 30 хв | Обсяг | Вільна смуга (60 − 17 Мбіт/с штатного трафіку) | Час |
|---|---:|---:|---:|
| Події й телеметрія | 1800 с × 0,17 Мбіт/с + події ≈ 37 МБ | 43 Мбіт/с | ≈ 7 с ≤ 120 с |
| Подійні фрагменти | 1800 с × 17 Мбіт/с ≈ 30,5 Гбіт (3,8 ГБ) | 43 Мбіт/с | ≈ 710 с ≈ 12 хв ≤ 15 хв |

Місткість Local Event Buffer не обмежує сценарій: 37 МБ за 30 хв проти 256 ГБ.

### Тактики та їхня ціна

| Тактика | Що змінює | Що погіршує |
|---|---|---|
| Виявлення відмови: таймаут Sync Agent 10 с | Час переходу в режим «без сервера» | Хибні переходи за короткочасних збоїв — повернення автоматичне |
| Локальне рішення з кешем політик | Доступність в'їзду | Застарілість кешу на час розриву |
| Store-and-forward (outbox) з ідемпотентними ID | 0 втрачених подій | Розходження в часі появи подій в архіві |
| Кероване зниження: фрагменти відкладаються, події — ні | Час синхронізації подій | Фрагменти доступні службі безпеки із затримкою до 15 хв |

### Процедура перевірки

1. Під час штатної роботи заблокувати маршрут edge-вузла до сервера правилом брандмауера.
2. Протягом 30 хв виконати 50 в'їздів дозволених номерів, 5 в'їздів недозволених, 20 виїздів, 100 змін стану місць і 3 ручні дії оператора.
3. Перевірити час кожної команди шлагбаума й наявність усіх подій у Local Event Buffer.
4. Відновити маршрут і виміряти час дренажу подій і фрагментів.
5. Звірити множини `event_id` на edge-вузлі та в Metadata DB.

### Критерій проходження

Усі локальні операції виконано, жодної підтвердженої команди не втрачено, дублікатів немає, події синхронізовано за ≤ 120 с, фрагменти — за ≤ 15 хв.

**Висновок:** у редакції 1.0 рішення про доступ ухвалював серверний Access Service, і крок «рішення про доступ» без сервера не мав виконавця — сценарій не витримувався. Зміна — Edge Access Control із кешем політик (ADR-0001, редакція 2). Тепер архітектура підтримує сценарій.
