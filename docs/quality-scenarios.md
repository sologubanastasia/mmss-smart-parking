# Сценарії атрибутів якості

## QS-01. Пікове навантаження на визначення зайнятості

**Атрибути:** продуктивність, масштабованість, мультимодальність.

| Елемент | Опис |
|---|---|
| Джерело стимулу | Автомобілі, камери та ультразвукові датчики |
| Стимул | Упродовж 30 с одночасно змінюється стан 50 місць, а 200 клієнтів запитують карту парковки |
| Середовище | Штатна робота: 50 камер, 500 датчиків, усі серверні вузли доступні |
| Артефакт | Video Analytics, Sensor Ingest, Time Synchronizer, Occupancy Fusion, Parking API |
| Реакція | Edge-вузол обробляє події, об'єднує модальності, сервер оновлює карту; за дефіциту ресурсів знижується частота некритичного відео, але сенсорні події та команди зберігають пріоритет |
| Вимірювана характеристика | p95 наскрізної затримки ≤2 с; збільшення p95 порівняно зі стендом на 100 місць ≤20%; розходження міток ≤200 мс для 99% подій |

**Забезпечується:** локальним Video Analytics і Occupancy Fusion, розділенням транспортів, двома екземплярами Parking API та керованим зниженням частоти аналізу відео. Див. ADR-0001 і ADR-0002.

### Процедура перевірки

1. Запустити генератор 500 сенсорів і 50 відеоджерел або їхніх стендових замінників.
2. Синхронно згенерувати 50 переходів `FREE ↔ OCCUPIED`.
3. Запустити 200 паралельних клієнтських запитів карти.
4. Зібрати мітки `stimulus_time`, `fusion_time`, `api_time`, `display_time`.
5. Обчислити p95 і порівняти з базовим прогоном для 100 місць і 10 камер.

### Критерій проходження

Усі три числові характеристики сценарію виконуються. Якщо p95 перевищує 2 с, перша зміна — збільшення кількості екземплярів Parking API; якщо затримка виникає на edge-вузлі — розділення зон між двома edge-вузлами.

## QS-02. Втрата зв'язку з центральним сервером

**Атрибути:** доступність, відмовостійкість, цілісність даних.

| Елемент | Опис |
|---|---|
| Джерело стимулу | Мережеве обладнання або провайдер зв'язку |
| Стимул | Зв'язок між edge-вузлом парковки та центральним сервером зникає на 30 хв |
| Середовище | Парковка працює; камери, датчики, локальний MQTT Broker і Gate Controller доступні |
| Артефакт | Video Analytics, Occupancy Fusion, Local Event Buffer, MQTT Broker, Gate Controller, Operator Dashboard, Sync Agent |
| Реакція | Визначення зайнятості й дозволені локальні операції продовжуються; події накопичуються з унікальними ID; оператор бачить режим деградації; після відновлення події синхронізуються без дублікатів |
| Вимірювана характеристика | Локальні функції працюють усі 30 хв; не втрачено жодної підтвердженої команди шлагбаума; накопичені події синхронізуються не довше ніж за 120 с після відновлення зв'язку |

**Забезпечується:** Local Event Buffer, локальним MQTT Broker, ідемпотентними ідентифікаторами подій та аварійним інтерфейсом оператора. Див. ADR-0001 і ADR-0002.

### Процедура перевірки

1. Під час штатної роботи фізично або програмно заблокувати маршрут до центрального сервера.
2. Протягом 30 хв створювати події зайнятості, два дозволені в'їзди, один виїзд і одну ручну дію оператора.
3. Перевірити локальне виконання й наявність усіх подій у Local Event Buffer.
4. Відновити зв'язок і виміряти час спорожнення буфера.
5. Звірити кількість унікальних ID на edge-вузлі та в Metadata DB.

### Критерій проходження

Усі локальні операції виконані, дублікати в Metadata DB відсутні, підтверджені команди не втрачені, синхронізація завершена за 120 с або швидше.
